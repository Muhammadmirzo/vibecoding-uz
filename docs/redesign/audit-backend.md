# Backend and Architecture Audit

## 1. Architecture and data flow

- **Presentation → boundary → database is the dominant pattern, not page/action → service → repository.** App Router pages render feature components; client hooks fetch mutation endpoints; most route handlers import Drizzle directly and contain validation, authorization, business rules, queries, and response shaping. Representative paths: `src/app/kabinet/page.tsx:16-37` → `/api/me` → `src/app/api/me/route.ts:8-139` → `users/userProfiles`; `src/features/quiz/DiagnosticQuiz.tsx:50-68` → `src/app/api/quiz/route.ts:32-89` → `leads`; `src/features/crm/components/Leads/useKanban.ts:16-22` → `src/app/api/admin/leads/route.ts:7-100` → `leads`.
- **Authentication:** login/OTP/Telegram handlers verify identity, create a `sessions` row, sign a token, and set a cookie; logout deletes the row. See `src/app/api/auth/login/route.ts:35-108`, `src/app/api/auth/otp/verify/route.ts:31-167`, `src/app/api/auth/telegram/route.ts:51-123`, and `src/app/api/auth/logout/route.ts:12-37`.
- **Course access:** lesson page/component → lesson API → `lessons/courseSections/courses` query → drip access service. See `src/app/kabinet/kurs/[id]/dars/[lessonId]/page.tsx:1-8`, `src/features/lms/components/LessonPlayerView.tsx:1-39`, `src/app/api/lms/lessons/[lessonId]/route.ts:9-41`, and `src/features/lms/drip/access.ts:12-73`.
- **Checkout/payment:** cabinet component → checkout route → trusted cohort price → pending `payments` row → provider URL; provider callback verifies the request, locks a transaction, marks payment paid, and activates enrollment. See `src/app/kabinet/to-lovlar/PaymentSummaryCard.tsx:48-66`, `src/app/api/payments/checkout/route.ts:35-100`, `src/app/api/payments/payme/route.ts:61-145`, and `src/app/api/payments/click/route.ts:55-119`.
- **CRM:** client hooks call admin APIs, which directly query/join CRM tables and emit audit records for selected mutations. See `src/features/crm/components/Cohorts/useCohorts.ts:1-5`, `src/app/api/admin/cohorts/route.ts:7-113`, and `src/app/api/admin/users/route.ts:31-153`.
- **Infrastructure:** Drizzle wraps a `postgres` client and exposes retry, health, and transaction-lock helpers (`src/db/index.ts:1-19`, `41-152`). The LMS drip service is a useful service-layer exception; pricing/refund helpers and certificates also exist, but are inconsistently adopted.
- **Operational flows:** cron dispatches drip, homework, and inactivity notifications (`src/app/api/cron/reminders/route.ts:17-118`). MCP declares seven tools but returns synthetic results rather than querying Drizzle (`mcp-server/index.ts:32-193`, `198-439`).

## 2. Domain model summary

- **Identity:** `users` is the identity aggregate; `userProfiles` is 1:1, `sessions` and `otpCodes` are dependent records (`src/db/schema/users.ts:4-47`). Role types include superadmin/admin/manager/mentor/student (`src/db/schema/enums.ts:3`).
- **Course delivery:** `courses` → `courseSections` → `lessons`; `lessonProgress` links a user to a lesson but lacks a user+lesson uniqueness constraint (`src/db/schema/courses.ts:5-58`).
- **Commercial:** `courses` → `cohorts` → `enrollments` → `payments`; enrollment holds lifecycle, certificate, and score, while payment holds provider/state/amount metadata (`src/db/schema/commercial.ts:6-43`). Job applications are not first-class: they are stored as `leads` with the form payload inside `quizAnswers` (`src/app/api/ish/apply/route.ts:23-57`).
- **Assessment:** `lessons` → `homeworkAssignments` → `homeworkSubmissions` → `homeworkReviews`, with users as submitters and mentors (`src/db/schema/homework.ts:6-32`). No DB uniqueness on one review per submission.
- **CRM:** `leads` references a recommended course and optional assigned manager (`src/db/schema/crm.ts:6-18`); pipeline status is stored directly rather than as a transition history.
- **Content:** `certificates` references enrollment and snapshots holder/course/score (`src/db/schema/content.ts:7-16`); `experts`, `testimonials`, `glossaryTerms`, `blogPosts`, and `siteSettings` form the content model (`src/db/schema/content.ts:18-78`).
- **Operations/marketing:** `broadcastNotifications`, `auditLogs`, `faqs`, `jobOpenings`, and `portfolios` (`src/db/schema/operations.ts:5-68`). There is no referral-account, referral-ledger, payout, refund, or provider-refund entity.

## 3. Prioritized code smells and boundary defects

- **P0 — Authentication state is split.** `validateSessionCookie` checks the backing session (`src/lib/auth/session/validate.ts:12-48`), but `getAuthSession` only verifies the signed token (`51-68`) and middleware trusts the token role (`src/middleware.ts:25-33`, `84-93`). This defeats logout/role revocation.
- **P0 — Telegram webhook is unauthenticated.** The endpoint forwards arbitrary JSON without checking Telegram's secret header or parsing it with Zod (`src/app/api/telegram/webhook/route.ts:4-24`).
- **P0 — Telegram linking permits takeover.** Contact linking trusts a submitted phone without requiring `contact.user_id === ctx.from.id` (`src/lib/telegram/handlers/contact.ts:22-31`); `/start <UUID>` can link by an arbitrary user ID through the `linkToken` branch (`src/lib/telegram/handlers/start.ts:12-22`, `src/lib/telegram/linkAccount.ts:40-54`).
- **P1 — Unsafe casts bypass type safety despite no literal `any`.** Payme/Click cast transaction callbacks from `unknown` (`src/app/api/payments/payme/route.ts:78-80`, `105-107`, `121-123`; `src/app/api/payments/click/route.ts:63-65`, `76-78`, `94-96`); session JSON is asserted to `Record<string, unknown>` (`src/lib/auth/session/token.ts:87-99`); admin role query input is cast to an enum (`src/app/api/admin/users/route.ts:16-18`).
- **P1 — Shallow client response validation.** Arrays are checked only with `Array.isArray` before domain-type assertions in `src/features/crm/components/Blogs/useBlogs.ts:6`, `Homework/useHomeworkQueue.ts:6`, `Users/useUsers.ts:10-11`, and `Notifications/useNotifications.ts:5-6`; no shared response schemas exist.
- **P1 — Zod is missing at several query/path boundaries.** Telegram webhook (`src/app/api/telegram/webhook/route.ts:22-23`); homework status (`src/app/api/admin/homework/route.ts:14-15`, `51-54`); analytics period (`src/app/api/admin/analytics/route.ts:8-9`); user role/search (`src/app/api/admin/users/route.ts:10-18`); audit action/search (`src/app/api/admin/audit-logs/route.ts:8-25`); portfolio limit/category (`src/app/api/portfolio/route.ts:11-12`); and multiple dynamic IDs.
- **P1 — Business logic is embedded in routes.** Payme/Click own state machines and fulfillment (`src/app/api/payments/payme/route.ts:61-145`; `src/app/api/payments/click/route.ts:55-119`); analytics owns funnel/revenue calculations and full-table scans (`src/app/api/admin/analytics/route.ts:11-138`); cohorts compute seats and early pricing in the handler (`src/app/api/admin/cohorts/route.ts:22-60`).
- **P1 — Components/hooks own orchestration and view transformation.** `useKanban` fetches/mutates/deletes (`src/features/crm/components/Leads/useKanban.ts:16-22`); `LessonPlayerView` normalizes API data (`src/features/lms/components/LessonPlayerView.tsx:8-35`); cohort hooks/modals own transport and form conversion (`src/features/crm/components/Cohorts/useCohorts.ts:1-5`, `CohortModal.tsx:1`).
- **P2 — Validation/calculation is duplicated and can drift.** Profile and password rules exist in both client and server (`src/features/lms/components/settings/useSettingsProfile.ts:66-109`; `src/app/api/me/route.ts:79-80`; `src/app/api/me/password/route.ts:19-20`); checkout duplicates early-price selection instead of using `calculateCoursePricing` (`src/app/api/payments/checkout/route.ts:73-86`; `src/lib/pricing.ts:52-87`).
- **P2 — Multi-write invariants lack transactions.** Profile update/upsert (`src/app/api/me/route.ts:94-139`), homework review (`src/app/api/admin/homework/[id]/review/route.ts:53-99`), user creation/audit (`src/app/api/admin/users/route.ts:119-148`), and checkout/audit (`src/app/api/payments/checkout/route.ts:80-100`) can partially commit.
- **P2 — Analytics and activity are not production-grade.** Analytics accepts but does not apply `period` and aggregates full tables (`src/app/api/admin/analytics/route.ts:6-18`, `65-138`); student activity returns mock data (`src/app/api/admin/students/activity/route.ts:4-160`).
- **P2 — God file (>300 lines):** `mcp-server/index.ts` is 475 lines and combines declarations, dispatch, fake business operations, and response construction (`mcp-server/index.ts:32-439`).

## 4. Prioritized business-logic flaws

- **P0 — Payme cancellation is mislabeled as refund.** `CancelTransaction` changes any payment to `refunded` without a provider refund and leaves enrollment active (`src/app/api/payments/payme/route.ts:120-130`, `29-39`).
- **P0 — Referral withdrawal amount is client-controlled.** Any authenticated user can submit arbitrary `amountSum`; the route only writes an audit row, with no earned-balance calculation, reservation, payout entity, or idempotency (`src/lib/validations/student.ts:34-39`; `src/app/api/referral/claim/route.ts:30-49`). Displayed referral history/balance are hardcoded (`src/features/lms/components/referral/useReferral.ts:26-85`).
- **P0 — Telegram account takeover** is possible through fabricated contacts and user-ID deep links, as described above.
- **P1 — New-student checkout is blocked and later checkout overcharges.** Checkout requires `enrollmentId`, but a new cabinet user derives it from existing payments (`src/app/api/payments/checkout/route.ts:48-50`; `src/app/kabinet/to-lovlar/page.tsx:61-65`). Once enrolled, checkout charges full current cohort price rather than selected installment/outstanding balance (`src/app/api/payments/checkout/route.ts:73-86`; `src/app/kabinet/to-lovlar/PaymentSummaryCard.tsx:48-64`).
- **P1 — Duplicate full-price payments are allowed.** There is no unique active-payment/enrollment or provider-transaction constraint (`src/db/schema/commercial.ts:31-43`), while each checkout inserts a row (`src/app/api/payments/checkout/route.ts:80-87`) and each callback can fulfill its own row (`src/app/api/payments/payme/route.ts:104-117`; `src/app/api/payments/click/route.ts:94-115`).
- **P1 — Certificates have no eligibility gate.** Issuance checks only that enrollment exists, defaults an absent score to `9.5`, then marks the enrollment finished; it does not require paid status or lesson/homework completion (`src/lib/certificates/service.ts:14-35`, `73-80`).
- **P1 — Cabinet certificate UI is fabricated/disconnected.** Holder, course, score, date, instructor, and code are hardcoded and the download button has no handler (`src/app/kabinet/sertifikat/page.tsx:11-64`).
- **P1 — Quiz scoring/recommendation is trusted from the client.** The route stores arbitrary answers/recommendation without verifying question completeness, option validity, or score derivation (`src/app/api/quiz/route.ts:40-72`; `src/lib/validations/crm.ts:24-34`).
- **P2 — Job applications are not tied to a real opening.** `jobId` is optional/non-UUID and never checked; no dedup or rate limit exists (`src/lib/validations/jobs.ts:21-34`; `src/app/api/ish/apply/route.ts:21-43`).
- **P2 — Refund support is not a workflow.** `src/lib/refund.ts:32-92` only calculates eligibility/amount; no caller executes or records provider refund, revokes access, or guarantees idempotency.
- **P2 — Provider availability lies about readiness.** Payment availability ignores required webhook secrets (`src/app/api/me/payments/route.ts:61-65`; `src/app/api/payments/payme/route.ts:42-48`; `src/app/api/payments/click/route.ts:34-37`).

## 5. Test coverage status

- **Present:** payment helper tests (`src/__tests__/hardening/payments.test.ts:1-35`), payment webhook hardening (`src/__tests__/payment-webhook.test.ts`), schema-focused CRM validation (`src/__tests__/crm/validations.test.ts:12-72`), Telegram auth helpers (`src/__tests__/telegram-auth.test.ts:6-63`), lead normalization (`src/__tests__/lead-telegram.test.ts:4-40`), and free-lesson lead tests (`src/__tests__/free-lesson-lead.test.ts:48-75`).
- **Gap — middleware:** its test duplicates role arrays and never imports `src/middleware.ts`; redirects, forged headers, cookie verification, and API 401/403 behavior are untested (`src/__tests__/auth/middleware.test.ts:3-22`; implementation `src/middleware.ts:8-9`).
- **Gap — critical routes:** no demonstrated route+DB coverage for Payme/Click state transitions, quiz insertion/scoring, Telegram webhook/linking, checkout idempotency, refund/revocation, certificate eligibility, referral payout, job opening integrity, or admin mutations/analytics.
- **Gap — MCP:** no execution tests cover the seven synthetic tool branches (`mcp-server/index.ts:199-439`).

## 6. Proposed target architecture and migration by risk

- **Target layout:** for each feature use `domain/` (entities, value objects, policies, errors), `application/` (use cases and transaction boundaries), `infrastructure/repositories/` (Drizzle implementations), `actions/` (Server Actions for UI mutations), `api/` (HTTP adapters only: parse, authorize, call use case, map result), and `ui/` (components/hooks consuming typed actions/read models). Shared primitives stay in `src/lib`; schemas remain the single boundary contracts in `src/lib/validations`.
- **1. Containment (immediate, lowest migration risk):** verify `X-Telegram-Bot-Api-Secret-Token`; require contact ownership; replace UUID deep-link linking with short-lived signed single-use tokens; require DB-backed session validation in middleware and handlers; disable referral claim/certificate issuance/mocked activity/MCP write-like tools until eligibility and persistence are implemented.
- **2. Financial correctness:** add payment/refund/payout ledgers and provider-reference uniqueness; model amount in minor units/decimal at domain boundaries; implement transactional checkout with one active obligation per enrollment; distinguish provider cancel, failed, charged, and refunded states; make callbacks idempotent and enrollment activation/revocation transactional.
- **3. Certificate and quiz policies:** introduce explicit eligibility policies requiring settled payment, active/completed enrollment, required progress/homework, and server-derived final score; recompute quiz answers/recommendation server-side; replace the certificate page with issued-certificate read models and the existing download service.
- **4. Extract application use cases:** move payment callbacks, pricing, analytics, cohorts, homework review, referral payout, and certificate issuance out of routes/components into typed use cases. Routes become thin and invoke services through explicit dependency interfaces.
- **5. Add repositories:** migrate read/write queries feature by feature, beginning with payments, referrals, certificates, quiz, then CRM. Use cases depend on repository interfaces; Drizzle implementations own SQL, locking, pagination, and mapping. Preserve current endpoints while adding adapters.
- **6. Enforce boundaries:** shared Zod request/response schemas; no client domain assertions; UUID/enum/query validation; transaction wrappers for multi-table invariants; explicit authorization service; structured domain errors mapped centrally to HTTP/UI results.
- **7. Verification rollout:** add contract tests at every schema, state-machine service, webhook fixture/replay, repository constraint, and authorization test. Migrate only after characterization tests cover current behavior and expected corrected behavior; finish with Playwright journeys for login/session revocation, first payment, duplicate callback, refund/revocation, quiz-to-lead, and certificate issuance/verification.
